# Security

- The browser does not store or receive Supabase access/refresh tokens during normal operation. Express stores them in `HttpOnly`, `Path=/api`, `SameSite=Lax` cookies (and `Secure` in production), validates access tokens with Supabase Auth, resolves membership from the database, and sends the user JWT with database requests so RLS remains active. The legacy `berry.auth.session` localStorage key is removed on app startup.
- Signup, login, password recovery, password update, refresh, and logout use Express endpoints backed by Supabase Auth. Authenticated API requests use cookies with credentialed CORS and exact allowed origins. Unsafe requests require an allowlisted `Origin`; this is the CSRF check. SameSite=None is only emitted in production, where Secure is enabled.
- Email confirmation and password recovery currently use Supabase's redirect fragment flow. The callback removes the fragment from browser history and immediately exchanges the tokens for HttpOnly cookies. An XSS executing at the callback before that exchange can still read the transient fragment; keep the callback free of third-party scripts and address XSS with a strict CSP and safe rendering.
- Every implemented tenant API route requires an organization header and checks active membership. Queries include the organization ID and RLS independently constrains the result.
- The organization-creation function is security-definer only to atomically create an organization and its first owner. It checks the caller identity and uses an empty `search_path`; execute access is limited to authenticated users.
- RLS is enabled on tables in the migration. Membership roles are not user-editable. Audit log mutation is denied.
- Task changes use a SECURITY DEFINER RPC with explicit role and assignment checks; authenticated users have no direct task update grant. Invoice/payment tables are direct-read only, and write operations use validated SQL functions.
- Private file objects live under an organization UUID folder in a private Storage bucket. Storage RLS checks active organization membership; downloads use one-minute signed URLs. File size and MIME type are restricted by the API and bucket configuration.
- Activity triggers write append-only audit entries and user-targeted notifications for organization business record changes.
- Express uses Helmet, JSON body limits, a configurable CORS allowlist, and rate limiting. Inputs are validated with Zod.
- Vercel static responses use `vercel.json` security headers and a CSP. The CSP allows HTTPS `connect-src` because the API origin is deployment-specific; narrow it to the exact API origin when the production hostname is finalized. For a Render static frontend, configure equivalent response headers in the Render Dashboard.
- Auth endpoint limits use Express's in-memory store. This is effective per process for a single staging instance; use a shared rate-limit store or edge controls before scaling the API across multiple instances.

Before production, run Supabase security advisors, test tenant A/B with separate real accounts, validate every RLS and Storage policy in the deployed project, configure HTTPS and exact CORS/Auth redirect origins, add backups/monitoring, and finish authorization around the client portal and subscription modules. Keep frontend and API on the same site when possible. For different-site deployments, set `AUTH_COOKIE_SAME_SITE=None`, use HTTPS, and verify third-party cookie availability in supported browsers. No formal penetration test or live Supabase sign-in/refresh/revocation test has been run by this change.
